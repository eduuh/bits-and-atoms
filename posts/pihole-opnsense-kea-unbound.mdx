The goal is simple: every device on the network, on every VLAN, gets Pi-hole for DNS. No exceptions, no per-device config, no relying on people to set it manually.

Getting there with OPNsense takes a few more steps than the Pi-hole docs suggest. Here's the full picture.

## The DNS chain

Before touching anything, it helps to know what you're building:

```
Client
  → Pi-hole (192.168.1.20:53)   filters ads and trackers
  → Unbound  (192.168.1.1:53)   OPNsense recursive resolver
  → internet
```

Pi-hole sits in front. It handles the filtering. Anything that isn't blocked gets forwarded to Unbound, which resolves it. Clients point at Pi-hole, not at OPNsense directly.

This gives you per-client stats in Pi-hole's dashboard. It sees real device IPs, not just the router's IP.

## Kea DHCP: the DNS field that isn't there

OPNsense's newer Kea DHCP server replaced the old ISC DHCP. The subnet editor looks clean, but there's no obvious "DNS Servers" field. You get things like Domain name, Domain search, Time servers. But not the one you actually need.

The reason: Kea stores everything as DHCP options internally. DNS servers are option 6 (`domain-name-servers`). You add it through the DHCP option data text area using JSON.

Go to Services → Kea DHCP → Subnets → [subnet] → Edit.

First, uncheck **Auto collect option data**. That checkbox silently pushes Unbound's IP as the DNS server. Uncheck it, or it'll override whatever you set.

Then in the DHCP option data field:

```json
[
  {
    "name": "domain-name-servers",
    "data": "192.168.1.20"
  }
]
```

Save. Repeat for every subnet: LAN, each VLAN, guest WiFi.

Clients pick it up on the next DHCP renewal.

## Firewall rules for VLANs

LAN is fine. It's on the same subnet as Pi-hole (`192.168.1.x`), so traffic flows directly.

VLANs and guest networks are isolated by default. They can't reach `192.168.1.20` without an explicit allow rule, which means DHCP hands out Pi-hole's IP but DNS queries get silently dropped. The symptoms look identical to a DNS outage.

For each VLAN and the guest interface, go to Firewall → Rules → [interface] → Add (at the top):

| Field | Value |
|-------|-------|
| Action | Pass |
| Protocol | TCP/UDP |
| Source | [interface] net |
| Destination | `192.168.1.20` |
| Destination port | DNS (53) |

Add this rule above any existing block-LAN rule. On guest networks especially, this should be a narrow exception: DNS to Pi-hole only, not general LAN access.

## Unbound: make sure it's not forwarding to Pi-hole

Pi-hole forwards to Unbound. Unbound must not forward back to Pi-hole. That loop kills DNS silently.

Go to Services → Unbound DNS → General.

- Enable Forwarding Mode: unchecked. Unbound resolves recursively, no upstream needed
- Confirm nothing under Query Forwarding points to `192.168.1.20`

Unbound is also where local hostnames come from (devices registered via Kea DHCP leases). Pi-hole can resolve those too, covered in the next step.

## Pi-hole: set Unbound as upstream

In Pi-hole admin (`http://192.168.1.20:8080/admin`), go to Settings → DNS.

Uncheck all the preset upstream servers. Under Custom DNS servers, add:

```
192.168.1.1
```

That's OPNsense's LAN IP. Unbound is listening there.

While you're in DNS settings, enable **Conditional Forwarding**:

- Local network: `192.168.1.0/24`
- Router IP: `192.168.1.1`

This lets Pi-hole resolve local hostnames (like `nas.local` or device names) by asking Unbound, which knows about Kea's DHCP leases.

Also confirm Pi-hole's own DHCP server is disabled. Settings → DHCP. Kea handles DHCP, so Pi-hole shouldn't be running a competing one.

## Verifying it works

Check a client got Pi-hole as DNS after renewing DHCP:

```bash
# macOS
scutil --dns | grep nameserver

# Linux
resolvectl status | grep "DNS Servers"
```

Should show `192.168.1.20`.

Test the full chain:

```bash
dig google.com @192.168.1.20   # Pi-hole resolves it
dig google.com @192.168.1.1    # Unbound resolves it
```

Both should return answers. If Unbound fails, it's not listening or the LAN interface isn't selected.

Test blocking:

```bash
dig doubleclick.net @192.168.1.20
```

Should return `0.0.0.0` or `NXDOMAIN`. Pi-hole's blocked count should increment.

For VLANs, from a device on a VLAN, run `dig google.com`. If it times out, the firewall rule is missing or below the block-LAN rule.

The live query log confirms per-client IPs are showing up:

```bash
ssh solar-assistant 'pihole -t'
```

If you only see `192.168.1.1` in the log, clients are hitting Unbound first. The Kea option data isn't saved correctly, or clients haven't renewed DHCP.

---

*The "Auto collect option data" checkbox is the one that gets you. It looks harmless, does something significant, and there's nothing nearby that explains it. Uncheck it before adding your Pi-hole option or it'll quietly win.*
